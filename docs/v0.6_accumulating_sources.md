# v0.6 累積型來源（Accumulating Sources）

## 目的

讓 Memosyne 能正確處理「同一份檔案會被多次匯入、後一次涵蓋前一次」的記憶來源——這類來源是常態（Gemini 對話續寫、Slack/Discord/WhatsApp 匯出、journal 追寫），不是邊角案例。

## 問題定義

目前 ingest pipeline 隱性假設「檔名等於內容」：

| 階段 | 判斷依據 | 內容變更時行為 |
|------|---------|--------------|
| ingest | `dst.exists()` | 跳過，但 spring 原檔仍歸檔 → 靜默資料遺失 |
| enrich | `enriched_at` 字串存在 | 跳過 → YAML 停留在舊版 |
| vectorize（增量）| chunk_id 已存在 | filter 掉新 chunks → 索引不更新 |
| vectorize `--rebuild` | wipe collection | 重建但讀的還是舊 enrichment |
| contextual cache | `{rel_path}::para{i}` | 用舊摘要套新段落 → 語意錯位 |
| Tapestry | 由 enrich 觸發 | enrich 跳過 → 圖譜不更新 |

三層獨立的「跳過」邏輯導致：

1. 同 thread 續寫的新訊息完全遺失，且無錯誤訊息
2. 若強制覆蓋檔案，三層不同步 → vault / YAML / vector / cache / graph 各自停在不同版本
3. 若新內容段落數變少，舊 `::para3,4,5` 留在 Chroma 變孤兒 chunk

## 設計：兩層去重

### File 層 — content_hash

每份 vault 檔的 frontmatter 加：

```yaml
content_hash: "sha256:abc123..."       # body 的 hash（去掉 frontmatter）
filename_origin: "conv_abc123.md"      # spring 原檔名
source_thread_id: "1120d08bfe9c35a5"   # Gemini conv hash（其他 source 可為空）
revision: 2                            # 累計更新次數
```

Ingest 時用 file content_hash 攔截「兩次 export 完全一樣」——秒跳，連 parse 都不用。

### Turn 層 — turn ledger

把記憶的**身分單位**從「檔案」下移到「turn / 段」。Chronicle DB 加：

```sql
CREATE TABLE turn_ledger (
  turn_hash    TEXT PRIMARY KEY,        -- sha256(normalized turn text)
  memory_uuid  TEXT NOT NULL,           -- 屬於哪份 vault 檔
  turn_index   INTEGER NOT NULL,        -- 在該檔內第幾個 turn
  source       TEXT NOT NULL,           -- gemini / slack / journal / ...
  ingested_at  TIMESTAMP,
  enriched     BOOLEAN DEFAULT 0,
  embedded     BOOLEAN DEFAULT 0
);
CREATE INDEX idx_turn_ledger_memory ON turn_ledger(memory_uuid);
```

Ingest 流程改成：

```
1. File content_hash 比對 → 完全相同直接跳過
2. 偵測 accumulating source（gemini / claude / slack / journal_append…）
3. parse_turns(source, content) → list[Turn]
4. 對每個 turn 算 hash，查 ledger
   ├── 全部命中  → 純重複，跳過
   ├── 部分命中  → 續寫，只處理新 turns
   └── 0 命中    → 新對話（或撞檔名的不同對話）
5. 對新 turns：
   - 更新 vault 檔（人類可讀的完整版本）
   - 只對新 turns 跑 enrich，傳上下文，merge 進現有 YAML
   - 為新 turns 加 chunks，chunk_id 用 turn_hash 而非 ::para{i} 序號
   - 寫入 ledger
```

## 關鍵設計決策

### 為何不單純用 content_hash 整檔比對？

對 accumulating source，「整檔每次都不同」是常態。整檔比對只能告訴你「不一樣」，無法區分：

- 續寫（superset）→ 應該增量
- 編輯歷史 turn（divergent）→ 應該 warn
- 完全不同對話撞檔名 → 應該另建記憶

turn-level hash 自然處理這三種。

### Chunk id 改用 turn_hash 的好處

| 現況 `{rel_path}::para{i}` | 改成 `{rel_path}::{turn_hash}` |
|---|---|
| 段落數減少 → 留下孤兒 chunk | 刪 turn 就乾淨刪 chunk |
| 中間插入新段 → 後續 index 全位移 → 索引全失效 | 新 turn 各自獨立 id |
| 無法 turn-level dedup | 天然支援 |

### Enrichment 的 merge 策略

新 turns 的 enrichment 結果如何併進舊 YAML：

- `locations / people / events / emotions` — set union
- `themes` — set union，可考慮 top-N 截斷
- `personal_facts` — append（事實是時序性的，不該蓋掉舊事實）
- `importance` — 取 max（高重要不該被新內容稀釋）
- `period` — 不動（首次寫入後就 frozen）
- `summary` — **重新生成**，因為 summary 是全文的精華而非實體列表

需要決定的開放問題：是否要保留 enrichment 的時序版本歷史（每次 update 都留下 snapshot），對 Aletheia correction 流程有助益但增加儲存。

### Parser 介面

```python
class TurnParser(Protocol):
    source: str
    def can_parse(self, content: str) -> bool: ...
    def split_turns(self, content: str) -> list[Turn]: ...

@dataclass
class Turn:
    index: int
    role: str        # "user" / "assistant" / "self" / ...
    text: str
    timestamp: str | None
    raw: str         # 原始片段，給 hash 用
```

各來源各自實作：

- **GeminiParser**: `## 使用者` / `## Gemini` heading 分割
- **ClaudeParser**: `## Human` / `## Assistant`
- **JournalAppendParser**: `## YYYY-MM-DD` 日期 heading
- **SlackParser** / **DiscordParser**: 時間戳 + 使用者名格式（之後）

## 落地階段（v0.6 實作狀態）

### ✅ Phase 0 — 防漏（已完成）

實作於 `ingest.py`：

- 每次 ingest 計算 spring 內容的 `body_hash`（normalize 後 sha256）並
  寫入 vault 檔的 frontmatter `content_hash: "sha256:..."` 欄位
- `dst` 已存在時：hash 相同 → `skipped_same`；hash 不同 → 走 Phase 1
  turn-aware 流程；若不可解析則 warn + **不歸檔 spring 原檔**
- 改用 `IngestResult(action, dst)` 取代 `Optional[Path]`，讓「該歸檔嗎」
  「該再 enrich/vectorize 嗎」分開判斷

### ✅ Phase 1 — Gemini turn ledger（已完成）

實作於 `turns.py` + `turn_ledger.py` + `ingest.py::_try_turn_aware_gemini_update`：

- `chronicle.db` 加 `turn_ledger` 表（schema 詳見 `turn_ledger.py` docstring）
- `GeminiParser` 切 `## 使用者` / `## Gemini` heading（handles `## Gemini`
  followed by `## Gemini 說了` double-header quirk）
- ingest 對 gemini source 走 turn-aware diff：
  - 第一次 update 時自動 backfill 舊 dst 的 turns 到 ledger
  - 算 `spring_turns - known_hashes` 得到真正新 turns
  - 0 new → `skipped_same`；>0 new → 寫新 dst（保留 uuid、bump
    date_updated、清掉 enriched_at、refresh content_hash）、寫 ledger、
    寫 `dirty_paths.txt` marker
- vectorize.py 加 `refresh_paths(paths)` 與 build_index 啟動時自動消費
  dirty marker → 更新檔案的 chunks 被 deleted-then-rebuilt，
  解決 chunk_id 命中誤判為已索引的問題

**enrich 採用「重新處理整檔」策略**（不是只處理新 turns）。理由：clear
`enriched_at` 後 enrich.py 視為未處理，re-enrich 整檔結果正確，只是
LLM cost 比 partial 高。Partial enrichment 是 Phase 3 work。

### ✅ Phase 2 — Parser 抽象化（已完成）

實作於 `turns.py`：

- `TurnParser` Protocol + `Turn` dataclass
- 3 個 parser：`GeminiParser`、`ClaudeParser`、`JournalAppendParser`
- `detect_parser(content, hint)` registry
- `route_journal` 已 wire `JournalAppendParser`：含 ≥2 個
  `## YYYY-MM-DD` heading 的 journal 走 day-level turn-aware 更新

`ClaudeParser` 已實作但尚未在 ingest 路由（vault layout 沒有 Claude
專屬目錄；要用時加一個 `route_claude` 即可）。

### ⏳ Phase 3 — Enrichment merge 策略（部分完成 / 後續）

**已完成：**
- Frontmatter `content_hash` / `date_updated` 維護完善
- Update 時清掉 `enriched_at` 讓 enrich.py re-process

**未完成（v0.6.1 或 v0.7）：**
- 只 enrich 新 turns + merge 進現有 YAML 的 partial mode
- YAML field union 規則（locations/people/events/emotions = set union；
  themes top-N union；personal_facts append；importance max；
  period frozen after first；summary regenerate）
- 是否保留 enrichment snapshot 歷史
- Aletheia correction 是否支援 turn-level

**風險評估**：current full re-enrich on update 行為正確但 LLM 成本高。
對於每次更新只多 1-3 個 turn 的典型 Gemini 續寫，成本可接受。對於
200-turn 大對話頻繁更新的場景才需要 partial mode。
