## 延後項目

### WS4 — Migration helper（`memosyne embed migrate`）

切換 embedding model 時自動處理 Chroma collection 的 dim 變更，避免手動 `--full` 切錯 model 撞牆。

```bash
memosyne embed migrate --to nomic-embed-text --url http://gpu-host:11434
# → 確認 endpoint 可達
# → 跑一個 sample embed，回報 dim
# → 比對現行 Chroma collection 的 dim
# → 不符就：印出預估時間（依現有 chunk 數）→ 確認後跑 vectorize --rebuild + 切換 .env
```

實作要點：
- 新增 `embed migrate` subcommand（memosyne.py + 可能新檔或併入 embed_backend.py）
- 復用 `embed_backend.resolve_config()` / `ping_endpoint()` / `RemoteEmbeddingFunction.probe()`
- 讀現行 Chroma collection 的 dim（從既有 collection metadata 或 sample query）
- dim 不符才 rebuild；相符直接切 `.env` 即可

**建議處置**：真正部署遠端 GPU、且需要換 model 那天才需要。可留在 v0.8 backlog。

### WS5 — 部署文檔（`docs/deployment/distributed.md`）

完整 Mac + Windows/WSL recipe，目標是任何人讀完能 30 分鐘配通。分四段：

1. **Windows / WSL 端準備**：nvidia-smi 通、WSL 內裝 Ollama、`ollama serve` daemonize、`ollama pull nomic-embed-text`
2. **Networking**：Tailscale（推薦）vs LAN port forward；如何拿到穩定 endpoint URL
3. **Mac 端 `.env` 配置**：三個 `MEMOSYNE_EMBED_*` 變數；跑 `providers test embed` 驗證綠
4. **故障排除**：GPU 沒通、port 沒開、Tailscale 重連、latency 飆高、Chroma dim 不一致

**建議處置**：與 WS4 同批；實際部署時補上最有價值（邊配邊寫 recipe）。

### WS6 — Phase 3 partial enrichment（v0.6 遺留債）

> ⚠️ 此項**與分散式運算無關**，是 v0.6 deferred、v0.7 又 deferred 的舊債，只是被掛在 v0.8 計畫下。
> 建議直接搬進 v1.0 或獨立小版本處理，別讓它繼續跟著版本漂移。

讓 enrich 在 `_try_turn_aware_*_update` 路徑下只處理新 turns（而非整檔 re-process）：

- 抽出 `enrich_text(text, prior_enrichment=None)`，接受可選舊 YAML
- 對新 turns enrich → 與舊 YAML merge（field-level 規則）：
  - `locations / people / events / emotions` → set union
  - `themes` → set union，top-N 截斷
  - `personal_facts` → append（事實是時序的）
  - `importance` → max（高不該被稀釋）
  - `period` → frozen after first write
  - `summary` → 重新生成（含全文，不只新 turns）
- `ingest._try_turn_aware_gemini_update` 不再 `_clear_enriched_at`，改 mark 為「partial-pending」
- `enrich.py` 識別 partial-pending、只處理 diff、寫回 merged YAML

**驗收**：247-Gemini 中找一個已 enriched 的對話，append 5 個 turn 再 ingest → enrich 階段只 LLM call 1 次（不是整檔 re-process）。

**建議處置**：搬進 v1.0。
